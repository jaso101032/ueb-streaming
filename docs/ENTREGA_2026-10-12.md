# Entrega de continuidad — 12 de octubre de 2026

Este documento permite continuar UEBTV desde un árbol de trabajo limpio, sin
depender de conversaciones previas. Complementa el [README](../README.md) y
la [arquitectura multimedia](arquitectura-multimedia.md).

## Qué está implementado

### Experiencia pública

- `/senal` es el canal principal: prioriza un directo y, al terminar, retoma
  automáticamente el contenido programado.
- `/eventos` es el catálogo: búsqueda por título, facultad, categoría y estado.
  En teléfono los filtros se abren desde **Filtrar catálogo** para no ocupar
  espacio permanente.
- `/eventos/{evento}` es la sala de un evento: reproductor, contador externo
  de espectadores, datos desplegables, acciones y chat.
- El reproductor usa HLS/hls.js para los directos y video HTML nativo para
  grabaciones y videos programados. Mantiene la marca UEBTV; el indicador de
  directo aparece durante una emisión. El botón **Volver al directo** solo se
  muestra al quedar retrasado dentro de la ventana HLS disponible.
- Hay modo oscuro, navegación y tamaños adaptados para teléfono. Los controles
  del reproductor se ocultan tras inactividad y vuelven con una interacción.

### Comunidad y presencia

- Cualquier visitante puede leer el chat. Para enviar mensajes debe iniciar
  sesión. Cuando termina el vivo, el chat queda cerrado y se conserva como
  historial con su minuto de reproducción.
- Administración y operadores pueden retirar mensajes.
- El contador de espectadores es una presencia anónima: cada navegador genera
  un UUID local y envía un pulso mientras la sala está visible. La tabla
  `event_viewers` fue creada por la migración
  `2026_10_11_180000_create_event_viewers_table.php`.
- Los videos grabados y programados no muestran «espectadores conectados».
  Muestran visualizaciones acumuladas, registradas tras 3 segundos de
  reproducción efectiva y como máximo una vez por navegador y video cada día.
  Abrir o recargar la página no suma una vista. La migración
  `2026_10_12_200000_create_event_video_views_table.php` crea el registro
  separado; es una métrica aproximada de reproducciones, no de personas únicas.

### Operación administrativa

El menú se simplificó para evitar pantallas que parecen duplicadas:

| Sección | Responsabilidad única |
| --- | --- |
| **Resumen** | Panorama administrativo. |
| **Gestionar eventos** | Crear, editar, consultar eventos y sus grabaciones. |
| **Emitir con OBS** | Solo eventos pendientes que requieren señal de OBS. No muestra grabaciones terminadas ni videos programados. |
| **Parrilla 24/7** | Subir y procesar por separado programas con horario y publicidad institucional para los huecos. |
| **Catálogo público** | Ver la experiencia que recibe la audiencia. |

Flujo de un directo: `Gestionar eventos → Emitir con OBS → Ver sala pública → Gestión de grabación`.

Flujo de un video programado: `Parrilla 24/7 → Señal continua`.

La publicidad institucional tiene biblioteca y formulario propios en
**Parrilla 24/7**. La señal continua prioriza directo, luego programa y después
anuncio activo convertido; muestra «P» solo durante el anuncio. Si todavía no
se cargan piezas oficiales autorizadas, permanece la pantalla de espera entre
emisiones. Aplicar la migración `2026_10_12_210000_create_institutional_ads_table.php`
y mantener `scheduled:process --watch` activo.

## Arranque local comprobado

### 1. Preparar dependencias

```bash
composer install
npm ci
cp .env.example .env
php artisan key:generate
php artisan migrate
php artisan storage:link
```

Configura la base de datos antes de ejecutar `migrate`. No se debe compartir ni
versionar el archivo `.env`.

Para usar el proxy RTMP/HLS local, genera y guarda una sola vez un token de 64
caracteres hexadecimales en `.env`:

```bash
php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
```

Asigna el resultado a `STREAMING_CALLBACK_TOKEN=`. El script local se detiene
de forma intencional si el valor falta o no tiene el formato correcto.

### 2. Iniciar aplicación y streaming

En una terminal, compila los recursos y levanta Laravel para compartirlo en la
red local:

```bash
composer run share
```

En otra terminal, con Podman instalado, levanta el RTMP/HLS local:

```bash
bash scripts/start-local-rtmp.sh
```

El segundo comando crea el contenedor `uebtv-rtmp`, escucha RTMP en `1935` y
expone aplicación + HLS mediante el proxy `8080`.

| Dispositivo | Dirección de prueba |
| --- | --- |
| PC local | `http://127.0.0.1:8080/senal` |
| Teléfono en la misma red | `http://IP_DEL_PC:8080/senal` |
| OBS en el mismo PC | `rtmp://127.0.0.1:1935/live` |
| OBS en otro equipo de la LAN | `rtmp://IP_DEL_PC:1935/live` |

Obtén la IP con `ip -4 addr show`. El teléfono y PC deben compartir una red
sin aislamiento de clientes; permite TCP `8080` y `1935` si el firewall lo
requiere. Para detener el proxy: `podman stop uebtv-rtmp`.

> Para cambios solo visuales que se verán desde el teléfono, vuelve a ejecutar
> `composer run share` después de modificar código. `npm run dev` sirve para
> desarrollo con HMR en el PC, no es la opción recomendada para el teléfono.

## Límites que no deben presentarse como terminados

- La calidad adaptativa multibitrate tipo YouTube todavía no existe: requiere
  transcodificación HLS con varias representaciones en el servidor.
- La meta de retraso máximo de cinco segundos requiere una medición real entre
  OBS y dispositivos; el perfil actual está optimizado para baja latencia, pero
  no certifica ese valor sin prueba de red.
- El contador mide navegadores/sesiones activas recientemente, no personas
  únicas ni audiencia analítica de producción.
- La ejecución real de OBS, Podman/Nginx y la red local debe probarse en cada
  equipo. Las pruebas automatizadas cubren aplicación y no sustituyen una
  emisión real.
